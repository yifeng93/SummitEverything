Reviewed: 2026-10-10. This matrix records documented wire shapes, not account readiness or real-service verification. No provider request was made while preparing it. The user confirmed they administer the Feishu custom app and can grant additional permissions. The user supplied tenant and user scope lists; see the implementation handoff for the relevant names. Permission availability is therefore configurable and is not itself a blocker. Feishu's current documentation pages are dynamic and do not expose all endpoint-specific details through this review path; claims below that originate in existing contracts or SDK models remain provisional until rechecked against readable official docs. “Not established” means the capability must stay disabled until official evidence or a safe verification method is recorded.

## Adapter and failure rules

- Settings, status reads, configuration previews, page reloads and provider selection do not contact external providers.
- HTTP adapters use bounded timeouts, no automatic redirects, no retry for writes, response-size limits, strict response parsing and sanitized error mapping.
- User tokens are required for Feishu user resources. A missing scope disables only the affected capability and reports a user-readable reason.
- No raw credentials, OAuth code/state, material content, task title, prompt, provider body, or authorization header enters logs or diagnostics.
- The tests use HTTP stubs and synthetic data only. They do not prove account access, model quality, actual cost or OAuth registration.
- Failed, timed-out, malformed or unverifiable writes retain the action as unknown. Reconciliation is read-only and cannot infer success from title equality.
