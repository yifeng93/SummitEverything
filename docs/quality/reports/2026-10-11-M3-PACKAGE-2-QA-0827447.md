## 可复验缺陷

### QA-1：history purpose 无真实 UI 入口（C13）

真实浏览器问答页“答复方式”只有事实、比较、方案三类；没有 current/history 范围控件。组件提交请求时 `purpose` 固定为 `current`（`web/src/components/AskView.tsx:276`）。API 能接收 current/history，不足以替代要求的真实用户路径。期望用户可明确查询历史版本并看到效力标记；实际 UI 无法进入该范围。按包要求 FAIL。

### QA-2：多轮指代未进入检索（C14）

在真实 UI 同一对话先问“青岚计划目前的预算上限是多少？”，下一轮实际用户问题问“它呢？”。后一轮无 citation，展示没有可引用依据。代码中 `previous_user_questions` 被放入答案上下文（`src/summit_everything/api/app.py:1695-1703`），但检索只 embed 当前问题并据此 rerank（`src/summit_everything/retrieval/query.py:231,248`）。因此“历史用户问题存在于 provider payload”没有实现指代解析 / 有效召回。期望可以用真实 previous user question 解释“它”，再按本轮 current gate 重新资格复核；实际返回空依据。`.local` 的真实 UI / route / payload 复演日志和 AX 摘录见 `browser-ax-observations.md`、`raw-logs/`。

### QA-3：预算拒绝被 UI 误标为连接中断（C20 UI）

在 UI 选定 QA 角色，将表达偏好设到超过该角色 UTF-8 byte budget，再发起问题。`POST /api/v1/queries` 返回 HTTP 422，错误码 `context_budget_exceeded`，消息明确为角色说明超预算，且请求没有写入对话历史；UI 却标为“本次回答 · 连接中断”。这是被服务端明确拒绝的输入/预算状态，并无断流证据。期望显示预算错误并引导编辑；实际状态误导用户诊断网络。Uvicorn access log、payload/harness、AX 观察均在证据目录。

### QA-4：current 查询包含不相关项目引用（C19 relevance）

最小复现脚本：`evidence/.../harness/retrieve_diagnostics.py`；对应完整 capture：`retrieval-diagnostics.json` 与 `relevance-reproduction.json`。在工作库 B 中创建并确认三张合成页面，重建当前索引后，在 current / fact 模式查询：**“青岚计划的预算上限是多少？”**

- 青岚当前页 `00000000-0000-0000-0000-0000000003e9`：正文为“青岚计划的设备采购预算上限为 19 万元，负责人已确认。排期为 11 月启动；运维费用未提供。”；validity `current`；正文 SHA `555d63c48cb3218d7d58802c03e5b9acba1014dafb3dc981a82522412dba8ee1`，索引正文 SHA 相同，current 资格通过。FakeReranker 分数 `0.6363636364`，余弦相似度 `0.3592106041`。
- 朱雀当前页 `00000000-0000-0000-0000-0000000003ea`：正文为“朱雀项目的设备采购预算上限为 12 万元，负责人已确认。排期为 12 月启动；运维费用未提供。”；validity `current`；正文 / 索引 SHA 相同，current 资格通过。FakeReranker 分数 `0.2727272727`，余弦相似度 `0.1197368680`。
- 青岚旧页 `00000000-0000-0000-0000-0000000003eb`：旧预算 20 万元，validity `superseded`。向量候选里相似度 `0.5345224838`，但 current 资格明确为 false、无 rerank score，也未进入最终 citation。按产品 gate 正确排除，不算缺陷。
- endpoint 返回 HTTP 200，最终 citation 同时包含青岚当前页与朱雀当前页；provider `source_statements` 也同时收到两页内容，`missing_information=[]`。stub 最终自然语言答复是中性说明，没有编造新业务数值；本缺陷是另一个项目的事实以有效依据 / 引用送入针对青岚的答案，降低事实归属和来源精度，不能仅因 stub 文案中性而判通过。当前查询应只给青岚依据，或无依据时明确 missing，不应给朱雀事实作青岚问题的支持材料。

该缺陷是“无关 current 候选被收入最终 source/citation”，不是“旧 superseded 页漏过 gate”。首次出现“仅朱雀”的临时结果已撤回：QA PageWriter 将青岚正文从 18 万更新为 19 万后，profile A 索引未重建，`stale_pages=1`，资格门按内容 SHA 正确排除旧 chunk；剩余只有朱雀。这是 QA 测试步骤不完整造成的夹具错误，不计产品缺陷。完成重建索引后青岚当前页有效参与检索，复现仍返回青岚 + 无关朱雀，详见当前诊断 JSON。旧错误结论保留于原始运行日志供审计。

## PASS 证据摘要

- C19：真实 UI 运行事实、比较、方案三种模式；比较分别出现资料陈述 / 推断，方案分别出现资料陈述 / 建议 / 尚缺资料。对完全无关的“火星基地室内湿度是多少？”返回缺资料且无 citation、无臆造业务数字。QA-4 使 C19 总项仍为 FAIL。
- C20：角色 CRUD / 选择 / 编辑 / 删除实际可达；用户本人表达声明才允许生成记忆候选，候选先编辑再确认才 active；assistant 回答文本、伪造 ID 和引述 / 粘贴材料 canary 拒绝。候选 provenance 指向真实用户消息；重复候选创建和确认保持幂等，confirmation ID 异文冲突拒绝；活动记忆编辑 / 删除与来源可读。Provider capture 中角色指令与 active memory 真正进入请求上下文，pending memory 不在 `user_memories`。8000 个字符的当前问题原样传给 provider（SHA 一致），预算超限记 422 且 provider 调用数不增长；未静默截断当前问题。
- C14 幂等：先创建 user message / active memory / role 并发起 query，编辑 role 和 memory 后用相同 request ID 再请求，SSE 事件序列及语义数据相同，provider 调用保持 29；相同 ID 但 answer mode 不同返回 409。详见 `replay-context-results.json`。previous user questions 上限 8 且只取真实 user question，通过。
- C21：同工作库 A/B 两个 profile 使用不同本机状态库；workspace A/B 独立历史、角色、记忆和索引。先发现 A 已有其他 QA 合成材料，故改为 marker-based isolation；B-only 用户消息 / role / active memory 在 A 不出现，切回 B 后可见。同步 workspace manifest 只有共享库身份与内容，不含本机 profile 路径、角色、记忆或凭据。问答没有写正式知识页、动作或进度。
- C13 引用资格：当前查询拒绝 superseded chunk；历史 API 引用按 history gate；重开历史后 updated citation 保留原引文版本并显示版本已更新。可见的 UI current/history 入口仍失败，见 QA-1。
