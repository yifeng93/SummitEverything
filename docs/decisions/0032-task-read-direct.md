# ADR 0032：飞书任务读取不再二次确认

- 状态：采纳
- 日期：2026-10-30
- 范围：只影响「今日 → 待办任务」的读取交互；写入动作不变。

## 背景

日历读取已经在 [ADR 0031](0031-calendar-direct-read.md) 里取消了每次读取的范围确认：授权连接后点刷新直接读。但待办任务仍保留旧流程——点刷新先弹「本次任务读取范围」，要再点「确认并读取任务」才发请求。

用户的原话是「我都已经点了刷新，你再让我确认，那不耽误时间吗」。刷新动作本身就是读取意图，再要一次确认没有增加任何信息：弹层里写的「最多 20 条、最多 2 次 HTTP 请求」在用户点刷新时并不会改变。

## 决定

1. `feishu.tasks.read` 的 acceptance plan 仍然创建、仍然确认、仍然按 `plan_id` 计量请求次数，但不再在界面上停下来等用户点按钮。
2. 点击刷新 = 同意本次读取范围。失败或结果未知时不自动重发，错误照常显示。
3. 写入类动作（新建任务、修改任务、完成任务、项目进度）保持逐次确认，不变。
4. 首次连接飞书、授权身份、读取材料前的范围预览也保持，不变。

## 后果

- 待办任务与日历的读取交互一致，不再一个直读、一个要确认。
- 计划与请求上限的计量仍由后端保证，只是确认由前端在同一次点击内完成；这不改变「模型输出不能签发批准证明」的边界，因为读取不是批准。
- 若后续要恢复确认，只需在 `TasksPanel.loadTasks` 里把自动确认改回 `setPendingPlan`。

## 依据

- 用户 2026-10-30 对「今日」页的反馈。
- 同类先例：[ADR 0031 日历直读](0031-calendar-direct-read.md)。
